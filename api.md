# `src/api.py` — методическое указание

Этот документ описывает, **как программировать высокоуровневый интерфейс
управления Unitree B2** через модуль `src/api.py`, и какие приёмы
использовать при его расширении (добавление манипулятора Z1, новых
команд, камер и т.д.).

`api.py` устроен по классической схеме «фасад + бэкенды»:

```
             +------------------+
пользователь |      Robot       |    — единый фасад, публичные методы
             +------------------+
                |
        ------- mode -------
        |                  |
+-----------------+ +-------------------+
| _BallBackend    | | _VelocityBackend  |   — реализуют один и тот же
+-----------------+ +-------------------+      внутренний интерфейс
        |                  |
    B2TargetEnv         B2VelEnv            — Genesis-окружения
        |                  |
          политика PPO (rsl_rl)
```

`Robot.move` / `Robot.rotate` / `Robot.set_target` делегируются бэкенду,
и внешний код **не должен знать**, какой из них активен — ради этого
API и создавался.

---

## 1. Публичный контракт `Robot`


| Член                                                         | Смысл                                                                        |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `Robot(exp_name, ckpt=-1, mode="ball", show_viewer=True, …)` | Создаёт `gs`-сцену и загружает веса. `mode` выбирает бэкенд.                 |
| `robot.pos` → `ndarray(3)`                                   | Позиция базы в мировой СК (`x, y, z`).                                       |
| `robot.yaw` → `float`                                        | Курс базы в мировой СК, радианы в `(-π, π]`.                                 |
| `robot.dt` → `float`                                         | Шаг интеграции симуляции.                                                    |
| `robot.env`                                                  | Доступ к нижележащему `B2TargetEnv`/`B2VelEnv` (побег из API).               |
| `robot.set_target(x=None, y=None, yaw=None)`                 | Обновить виртуальную мировую цель. `None` оставляет соответствующую ось.     |
| `robot.step(n=1)`                                            | Прокрутить политику + симуляцию `n` подшагов.                                |
| `robot.move(x, y, time)`                                     | «Иди в точку `(x, y)` в течение `time` секунд». Yaw фиксируется на текущий.  |
| `robot.rotate(yaw, time)`                                    | «Повернись в направлении `yaw` за `time` секунд». XY фиксируется на текущее. |
| `robot.close()`                                              | Высвободить debug-объекты вьювера.                                           |


Контракт одинаков для обоих модов.

## 2. Как именно реализован `move` / `rotate`

### 2.1. `mode="ball"`

`B2TargetEnv` принимает внешнюю цель `set_external_target(pos_xy, yaw)`
и отдаёт её политике как наблюдение в локальной СК. Политика обучена
гнаться за такой точкой.

Поэтому:

- `move(x, y, time)` = `set_target(x, y, yaw=current_yaw)` +
`_run_for(time)`.
- `rotate(yaw, time)` = `set_target(x=current_x, y=current_y, yaw=yaw)` +
`_run_for(time)`.

Больше ничего; всю работу делает сама сеть.

### 2.2. `mode="velocity"`

`B2VelEnv` ждёт **команды скорости** `(vx, vy, ω)` в теле робота. Чтобы
сохранить тот же «позиционный» контракт, `_VelocityBackend` поверх
политики строит простой П-регулятор:

```text
world_err = target_xy - base_xy                 # ошибка в мире
body_err  = R(-yaw) · world_err                 # в тело
vx_cmd    = clip(body_err_x · kp_lin, vx_lo, vx_hi)
vy_cmd    = clip(body_err_y · kp_lin, vy_lo, vy_hi)
ω_cmd     = clip(wrap(target_yaw - yaw) · kp_ang, ω_lo, ω_hi)
```

Диапазоны `[vx_lo, vx_hi]` и пр. **извлекаются из `cfgs.pkl`**,
написанного `b2_train_vel.py`, то есть из тех самых рамок, с которыми
тренировалась политика. Выходить за них нельзя — сеть никогда их не
видела.

Если политика обучена только «ехать вперёд 0.5 м/с»
(`lin_vel_x_range = [0.5, 0.5]`), то `mode="velocity"` в API почти
бесполезен — робот всегда поедет на 0.5 м/с независимо от ошибки.
Перед использованием убедитесь, что диапазоны команды тренируемы
(см. `README.md §2.2`).

## 3. Как добавлять свои высокоуровневые методы

Общая последовательность:

1. **Вычислить интент.** Новая цель может быть задана как «точка в
  мировой СК», «смещение от текущей позы», «заранее проложенный путь».
   Всё это в итоге сводится к паре `(target_xy, target_yaw)` и/или
   прямому воздействию на DOF.
2. **Сконвертировать в `set_target(...)` или в запись DOF** — в
  зависимости от того, чем управляет метод:
  - Движение базой → `self.set_target(...)` (бэкенд сам разберётся с
  модой).
  - Движение суставов манипулятора → прямой вызов
  `self.env.robot.control_dofs_position(...)` (см. §5).
3. **Прокрутить симуляцию** `self._run_for(time)` либо `self.step(n)`.

Шаблон нового метода:

```python
def move_relative(self, dx: float, dy: float, time: float) -> None:
    """Сместиться относительно текущей позы на (dx, dy)."""
    cx, cy = self.pos[0], self.pos[1]
    self.set_target(x=cx + dx, y=cy + dy, yaw=self.yaw)
    self._run_for(time)
```

Такой код **одинаково** работает и в `ball`, и в `velocity` — это
преимущество фасада.

## 4. Как добавлять новый бэкенд (новую политику)

Если через месяц появится третья политика (например, с прыжками), её
добавление выглядит так:

1. Написать среду `b2_jump_env.py` (аналог `B2TargetEnv`/`B2VelEnv`)
  и тренировочный скрипт; в `cfgs.pkl` оставить стабильную сигнатуру.
2. Реализовать класс `_JumpBackend` в `api.py`, дублирующий **интерфейс
  бэкенда**:

  | Атрибут / метод         | Сигнатура                                      |
  | ----------------------- | ---------------------------------------------- |
  | `pos` (property)        | `-> ndarray(3)`                                |
  | `yaw` (property)        | `-> float`                                     |
  | `dt` (property)         | `-> float`                                     |
  | `env` (property)        | `-> B2JumpEnv`                                 |
  | `set_target(x, y, yaw)` | Как интерпретировать цель — решает сам бэкенд. |
  | `step(n)`               | Шаг политики + сим.                            |
  | `close()`               | Уборка debug-объектов.                         |

3. В конструкторе `Robot.__init__` добавить ветку:
  ```python
   elif mode == "jump":
       self._backend = _JumpBackend(log_dir, ckpt_id, show_viewer, draw_target)
  ```
4. В `README.md` и в `api.md` добавить строку о новом моде.
5. Обновить `validate cfgs.pkl size`-блок: если в логах новой политики
  другое число полей, проверка `len(payload) != …` должна это ловить.

`move` / `rotate` менять не нужно.

## 5. Работа с дополнительными DOF (пример — манипулятор Z1)

RL-политика в этом проекте **никогда не управляет рукой**. Руку всегда
водит человек императивным кодом, через `control_dofs_position`.

### 5.1. Индексы DOF

```python
ARM_JOINT_NAMES = ["Joint01", "Joint02", "Joint03",
                   "Joint04", "Joint05", "Joint06"]

arm_dof_idx = torch.tensor(
    [env.robot.get_joint(n).dof_start for n in ARM_JOINT_NAMES],
    dtype=gs.tc_int, device=env.device,
)
```

Запишите индексы один раз (в конструкторе среды или в расширении
`Robot`), чтобы не дёргать `get_joint()` в горячем цикле.

### 5.2. PD-коэффициенты

```python
env.robot.set_dofs_kp([200.0]*6, arm_dof_idx)
env.robot.set_dofs_kv([  8.0]*6, arm_dof_idx)
```

Подбирать под массу звеньев Z1; выше чем у ног — нормально.

### 5.3. Запись желаемых углов каждый шаг

```python
arm_target = torch.tensor([[0.0, 1.5, -1.0, 0.0, 0.0, 0.0]],
                          dtype=gs.tc_float, device=env.device)
env.robot.control_dofs_position(arm_target, arm_dof_idx)
```

Важно: эту запись **нужно повторять в каждом шаге** до вызова
`policy(obs)` + `env.step(actions)`. Так как RL-политика пишет только в
`slice(6, 18)` (12 суставов ног), две записи не конфликтуют.

### 5.4. Шаблон расширения `Robot`

```python
# в Robot.__init__(self, ...)
self._arm_target: torch.Tensor | None = None

def set_arm_joints(self, values) -> None:
    self._arm_target = torch.as_tensor(
        values, dtype=gs.tc_float, device=self.env.device
    ).view(1, -1)

# внутри _BallBackend.step / _VelocityBackend.step — перед policy(obs):
if self._arm_target is not None:
    self.env.robot.control_dofs_position(self._arm_target, self.env.arm_dof_idx)
```

После этого вызов выглядит естественно:

```python
r = Robot("b2-walk-omni", mode="velocity")
r.set_arm_joints([0.0, 1.5, -1.0, 0.0, 0.0, 0.0])
r.move(1.0, 0.0, time=3.0)
```

### 5.5. Обратная кинематика

Перевод «желаемая поза наконечника» → «углы 6 суставов» вынесен **из
API**. Кандидаты:

- `pinocchio` — самый быстрый (C++ ядро).
- `kinpy` — pure-Python, простой API.
- Встроенный `robot.get_link("<ee>").inverse_kinematics(...)` в Genesis.

Результат IK кладите в `set_arm_joints(...)`.

## 6. Соглашения, которых стоит придерживаться

1. **Никогда не вызывайте `gs.init(...)` вручную**, если уже создали
  `Robot`. В процессе `gs.init` вызывается ровно один раз.
2. **Один `Robot` на процесс.** Genesis не любит несколько сцен в
  одном интерпретаторе.
3. **Не трогайте `cfgs.pkl` руками** — он однозначно описывает среду,
  на которой обучена политика. Любое расхождение обсерваций между
   тренировкой и инференсом ломает сеть. Если правите среду, правьте
   и тренировку, и переучивайте.
4. **Высокоуровневые методы всегда детерминируют yaw или XY-цель**,
  которую оставляют неизменной. Без этого `velocity`-бэкенд начинает
   бесконечно «ползти» в сторону старого таргета. Правило:
   `move` фиксирует yaw, `rotate` фиксирует позицию.
5. **Таймер `time` — это wall-clock duration, не гарантия прибытия.**
  Политика может не успеть — это нормально. Проверять «дошли ли» —
   обязанность вызывающего (через `robot.pos`).
6. `**show_viewer=False` — честный headless.** Все отладочные сферы
  включены только при `draw_target=True and show_viewer=True`, так
   что никаких лишних render-вызовов в CI/обучении.
7. **Долгие сценарии — пишите как последовательность коротких
  `move`/`rotate`/`set_arm_joints`** и не забывайте `close()` в
   `finally:`, чтобы не копить отладочные сферы.

## 7. Мини-рецепты

### 7.1. Обойти квадрат 1×1 м

```python
from math import pi
from api import Robot

r = Robot("b2-walk-omni", mode="velocity", show_viewer=True)
try:
    waypoints = [(1, 0), (1, 1), (0, 1), (0, 0)]
    for x, y in waypoints:
        r.move(x, y, time=4.0)
except KeyboardInterrupt:
    pass
finally:
    r.close()
```

### 7.2. Покрутиться на месте на 360°

```python
r.rotate(r.yaw + 2 * pi, time=6.0)   # политика удержит yaw target-у хвост
```

Для `velocity`-мода это сработает только если
`ang_vel_range` включает достаточное ω (иначе сеть «не докрутит» — П-регулятор
ограничит себя тренировочным диапазоном).

### 7.3. Перехват и замена цели на лету

```python
r.set_target(x=2.0, y=0.0)          # начинаем движение
for _ in range(200):
    r.step(1)
    if r.pos[0] > 1.0:
        r.set_target(y=1.0)         # на полпути добавляем боковую составляющую
        break
r.step(400)
```

## 8. Checklist при изменении API

Когда расширяете `api.py`, пробегитесь по этому списку:

- Новый публичный метод есть в `Robot`, а не в бэкенде напрямую.
- Метод одинаково работает в обоих модах (или явно бросает
`NotImplementedError` в нерелевантном).
- Все новые параметры имеют разумные дефолты и типизированы.
- Добавлен пример использования в `README.md §3.3` или
в `api.md §7`.
- Если добавили мод/бэкенд — обновлён `Robot.__init__` и сообщение об
ошибке в `raise FileNotFoundError(...)` (там прописан путь к
тренировочному скрипту).
- Прогнан smoke-test:
`uv run python -c "from api import Robot; print(Robot.__init__.__doc__)"`.
- Прогнан headless-эпизод (без GPU):
`uv run python - <<'PY' …`.

Следование чеклисту поддерживает главное инженерное свойство модуля —
чтобы код верхнего уровня не зависел от того, какой политикой в данный
момент управляется B2.
